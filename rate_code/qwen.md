## 📋 TL;DR

Рабочий TUI-прототип LLM-чата с приятным внешним видом, но **не готовый к использованию код**: заявленный агентский режим отсутствует, Claude/Gemini провайдеры неработоспособны, API-ключи могут утекать по HTTP, а UI печатает `undefined`. Архитектура — монолит на глобальном mutable-стейте.

> ### 📊 Итоговая оценка: **4 / 10**

## 1. 🛠️ Архитектура и структура

### ❌ Проблемы

| # | Проблема | Где | Severity |
|---|----------|-----|----------|
| A1 | **Монолит на 760 строк.** UI, конфиг, провайдеры, парсинг, readline-цикл — в одном файле без единого `import` besides deps. Нет `ui.js` / `config.js` / `providers.js` / `chat.js`. | `index.js` (весь файл) | 🔴 High |
| A2 | **Глобальный mutable state** (`rl`, `queue`, `history`, `busy`, `cfg`) вместо явного DI/стора. Прямая гонка данных между readline-эмиттером и async-циклом обработки. | верх файла | 🔴 High |
| A3 | **Хрупкий самодельный readline-цикл.** Ввод пользователя во время `await fetch()` оседает в очереди `queue` и обрабатывается пакетом позже — команды вроде `/stop` не срабатывают вовремя, Ctrl+C во время запроса не прерывает его. | цикл `processQueue()` | 🟠 Medium |
| A4 | **Фиктивный функционал.** README декларирует режим `agent` (работа с файлами/командами). В коде настройка `mode: chat|agent` читается, но **ни на что не влияет** — ветки `agent` нет вообще. | `s.mode`, README | 🔴 High |
| A5 | **Отсутствует слой абстракции провайдеров.** Формат OpenAI (`/chat/completions`) захардкожен в единственной функции запроса; добавить нового провайдера = править центральный код. | функция запроса к API | 🟠 Medium |

### ✅ Что хорошо
- Конфиг изолирован в один JSON-файл с дефолтами и миграцией при загрузке.
- Команды чата собраны в единый dispatch-table (`cmds`), а не в if-else лес.

### 💡 Что исправить
- Разбить на модули ESM: `src/config.js`, `src/providers/{openai-compatible,anthropic,gemini}.js`, `src/ui.js`, `src/repl.js`.
- Заменить глобалки на замкнутый стейт-объект, передаваемый явно.
- Либо реализовать agent-режим, либо **вырезать его из README** (второе честнее).

## 2. 🔒 Безопасность и уязвимости

### ❌ Проблемы

| # | Уязвимость | Детали | Severity |
|---|-----------|--------|----------|
| S1 | **Ключ уходит по HTTP в открытом виде.** Код принимает `baseUrl` на `http:` и отправляет `Authorization: Bearer <api_key>`. Прокси-прослушка перехватывает ключ. Никакой проверки схемы при `/provider add`. | построение fetch-запроса | 🔴 **Critical** |
| S2 | **Секреты в plaintext.** API-ключи лежат в `~/.lockcode/config.json` без шифрования, без поддержки `${ENV_VAR}`-интерполяции, без установки `chmod 600` на файл. | сохранение конфига | 🔴 High |
| S3 | **Rate-limiting — фикция.** Поле `limitUsed` существует в структуре, но никогда не инкрементируется; `maxRequestsPerMinute` нигде не проверяется перед запросом. Защита от бесконечных циклов/авто-повторов отсутствует. | счётчики лимитов | 🟠 Medium |
| S4 | **Невалидированный пользовательский ввод в URL.** `baseUrl` из конфига подставляется в fetch без нормализации (`new URL()` + проверка протокола). Классический вектор для SSRF-подобных ошибок конфигурации (например, `file:` или внутренний адрес). | конкатенация endpoint | 🟠 Medium |
| S5 | **Полная история уходит каждому провайдеру.** При переключении провайдера контекст диалога (включая потенциально чувствительные данные) автоматически отправляется на новый (возможно, сторонний) эндпоинт. | отправка `history` | 🟡 Low |

### 💡 Что исправить (короткие примеры)

```js
// S1/S4 — валидация baseUrl ДО сохранения провайдера
const u = new URL(baseUrl);
if (!['https:', 'http:'].includes(u.protocol)) throw new Error('bad protocol');
if (u.protocol === 'http:' && !isLocalhost(u.hostname)) {
  warn('⚠ API key will be sent over plaintext HTTP');
}
```

- Поддержать `apiKeyEnv: "OPENAI_API_KEY"` как альтернативу ключу в открытом виде.
- Инкрементировать `limitUsed` и бросать ошибку при превышении окна.

## 3. 🏎️ Производительность и оптимизация

| # | Узкое место | Почему это проблема | Severity |
|---|-------------|---------------------|----------|
| P1 | **Нет streaming.** Ответ LLM ждётся целиком до таймаута. Для генерации на тысячи токенов — минуты «зависшего» терминала. | UX + ощущение «вешания» приложения | 🔴 High |
| P2 | **`wrap()` за O(n²).** Функция переноса текста вызывает regex-подсчёт ширины на каждой итерации цикла по символам; вызывается для каждого сообщения при каждой полной перерисовке экрана. | CPU-спам при длинных ответах | 🟠 Medium |
| P3 | **Полная перерисовка шапки/панели при каждом изменении настроек** вместо точечного обновления diff'ом. | Лишние ANSI-записи, мерцание | 🟡 Low |
| P4 | **Урезание контекста по числу сообщений (24), а не по токенам.** Окно модели считается по сообщениям → реальный запрос может превысить context window, API вернёт 400, юзер получит невнятную ошибку. | Обрыв диалога / платные ошибки API | 🟠 Medium |
| P5 | **Таймаут реализован без `AbortController`.** Зависший fetch держит соединение; запрос нельзя отменить из UI. | Зомби-соединения | 🟡 Low |

### 💡 Что исправить
- SSE/streaming через `response.body` + инкрементальный рендер.
- Кэш результатов `wrap()` (Map: строка → линии) или однопроходный алгоритм.
- Тримминг истории по оценённым токенам (`chars/4` минимум, лучше — `tiktoken`/`gpt-tokenizer`).
- Передавать `AbortSignal.timeout(ms)` в fetch.
